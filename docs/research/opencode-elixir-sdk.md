# Research: driving opencode sessions from Elixir (`opencode_sdk`)

Resolves #2 (part of #1). Researched 2026-08-12 against primary sources:

- `opencode_sdk` v0.1.88 source: https://github.com/UtkarshUsername/opencode-sdk-elixir (cloned, read directly)
- Hex release metadata: https://hex.pm/api/packages/opencode_sdk
- The OpenAPI spec the SDK is generated from (`priv/opencode_openapi.json` in the SDK repo, captured from opencode server ~v1.1.53 per the README's health example)
- Official opencode docs: https://opencode.ai/docs/server/, /docs/sdk/, /docs/permissions/, /docs/providers/, /docs/config/
- opencode server source (now at https://github.com/anomalyco/opencode) for the `x-opencode-directory` header

## TL;DR

The SDK is a thin, usable OpenAPI-generated wrapper over the opencode HTTP server: everything we need exists (spawn server, per-request workspace directory, prompt, SSE events, `permission.asked` / `question.asked` / `session.idle` / `session.error`, reply endpoints, per-session model + permission ruleset). But its value-add over calling the server with Req directly is small — the hand-written core is ~450 lines, responses come back as plain string-keyed maps (the generated structs/typespecs are never instantiated), the SSE stream has no reconnect logic, and the server process wrapper is a bare `Port` with no supervision. Given release churn (89 releases in 6 months, tracking a spec that itself churns), recommendation: **pin exact (`{:opencode_sdk, "0.1.88"}`) and treat it as a reference implementation we can vendor/replace with ~2 small Req modules if it stalls.** The real coupling risk is to the opencode server API, not to this package.

## 1. API surface

Hand-written core (4 modules, everything else is generated):

- `OpenCode.create/1` — spawns `opencode serve --hostname=... --port=...` via `Port.open({:spawn_executable, ...})`, passes `:config` map as `OPENCODE_CONFIG_CONTENT` env (JSON), waits for the `"opencode server listening"` stdout line or `/global/health`, returns `%{client, server}`. `OpenCode.create_client/1` connects to an existing server (`:base_url`, `:directory`, `:headers`, `:timeout`). `OpenCode.close/1` / `OpenCode.Server.close/1` closes the port. (`lib/opencode.ex`, `lib/opencode/server.ex`)
- `OpenCode.Client.request/1` — Req-based; the "client" is just a keyword list (`[client: OpenCode.Client, base_url: ..., directory: ...]`) passed as the last arg to every operation. (`lib/opencode/client.ex`)
- `OpenCode.Generated.Operations` — ~115 endpoint functions generated by `oapi_generator` from the bundled spec. Session lifecycle: `session_create/2`, `session_list/1`, `session_delete/2`, `session_update/3`, `session_fork/3`, `session_abort/2`, `session_status/1`, `session_messages/2`, `session_diff/2`, `session_revert/3`. Also `worktree_create/list/remove/reset`, `experimental_workspace_*`, `config_get/update`, `provider_list`, `auth_set`, TUI and PTY control.

### Prompting

- `Operations.session_prompt(session_id, body, client)` → `POST /session/{id}/message` — **synchronous**: blocks until the turn completes, returns `{:ok, %{"info" => assistant_message, "parts" => [...]}}` (part types: `"text"`, `"reasoning"`, `"tool-invocation"`, `"step-start"/"step-finish"`, `"file"`, `"patch"`). Client default `receive_timeout` is `:infinity`, so long turns work.
- `Operations.session_prompt_async(session_id, body, client)` → `POST /session/{id}/prompt_async`, returns 204 immediately — this is the right shape for us: fire the prompt, then drive everything off the event stream.
- Prompt body (from the spec): `parts` (required), `model: %{providerID, modelID}`, `agent`, `system`, `tools: %{tool_name => boolean}`, `noReply` (inject context without triggering a reply), `format`, `variant`.
- Errors: non-2xx → `{:error, {status, body}}`; transport → `{:error, %Req.TransportError{}}`.

### Per-session working directories

- `Session` schema has a `directory` field, but `POST /session` body does **not** accept one (body: `parentID`, `title`, `agent`, `model`, `metadata`, `permission`, `workspaceID`). Directory is selected **per request**: the client keyword's `:directory` is sent as an `x-opencode-directory` header (`OpenCode.Client.add_directory/2`) and every generated op also forwards `directory`/`workspace` as query params. Verified server-side: `packages/opencode/src/server/shared/workspace-routing.ts` in anomalyco/opencode references both the `directory` query param and the `x-opencode-directory` header.
- So: one shared server, one client keyword list per bench workspace (`OpenCode.create_client(base_url: url, directory: workspace_dir)`), create the session through that client. The server resolves project/config per directory.

## 2. Events: detecting "asks a question", "done", errors

`Operations.event_subscribe(opts)` → `GET /event` (SSE). The hand-written client special-cases this URL (`sse?/1` matches `/event` and `/global/event`) and returns `{:ok, %{stream: stream}}` — a lazy Elixir `Stream` of JSON-decoded maps (spawn_linked reader process, hand-rolled `data:` parsing). Filterable by `directory`/`workspace` query params. `global_event/1` (`GET /global/event`) is the cross-instance variant. Stream starts with `server.connected` (per official server docs).

Event `type` strings we must react to (all confirmed in the spec / generated modules):

| Signal | Event type | Payload |
| --- | --- | --- |
| Coder asks a question | `question.asked` | `QuestionRequest`: `id`, `sessionID`, `questions: [QuestionInfo{question, header, options, multiple, custom}]`, `tool` |
| Question resolved | `question.replied`, `question.rejected` | request id |
| Permission needed | `permission.asked` | `PermissionRequest`: `id`, `sessionID`, `permission`, `patterns`, `metadata`, `always`, `tool{messageID, callID}` |
| Permission resolved | `permission.replied` | — |
| Coder done (turn finished, session idle) | `session.idle` | `{sessionID}` |
| Error | `session.error` | `{sessionID, error}` (union incl. provider-auth, context-overflow, unknown) |
| Progress/streaming detail | `message.updated`, `message.part.updated`, `message.part.delta`, `session.status`, `session.updated`, plus fine-grained `session.next.*` (text/reasoning/tool started/delta/ended, `session.next.tool.error`, step started/ended) | — |

Reply endpoints (also usable via polling — `question_list/1` (`GET /question`) and `permission_list/1` (`GET /permission`) list pending requests, so a dropped SSE connection is recoverable):

- `Operations.question_reply(request_id, %{answers: [[label, ...]]}, client)` → `POST /question/{id}/reply`; `question_reject(request_id, client)`.
- `Operations.permission_reply(request_id, %{reply: "once" | "always" | "reject"}, client)` → `POST /permission/{id}/reply` (newer route); `permission_respond(session_id, permission_id, body, client)` → `POST /session/{id}/permissions/{permissionID}` (older route, what the JS SDK docs show as `postSessionByIdPermissionsByPermissionId`).

Reliability caveat (flagged, not fully verified): `session.idle` marks "turn finished/idle", which fires after `session_prompt_async` completes a turn — including turns that ended because a question/permission is pending was **not** verifiable from docs alone; the safe pattern is to treat `session.idle` as "done" only when no pending question/permission exists for that session (check `question_list`/`permission_list`). The SDK's SSE stream has **no reconnect/backoff**; wrap consumption in our own supervised process and re-subscribe + re-list pending requests on failure.

## 3. Unattended runs (auto-approve)

Three layers, all verified:

1. **Config** (docs/permissions): `"permission"` key with `allow | ask | deny` per tool and glob patterns, last matching rule wins: `%{permission: %{"*" => "allow", "bash" => %{"*" => "allow", "rm *" => "deny"}}}`. Pass it via `OpenCode.create(config: %{permission: ...})` → `OPENCODE_CONFIG_CONTENT`, or per-project `opencode.json` in each workspace dir.
2. **Per session**: `session_create` body accepts `permission: [PermissionRule]` (`PermissionRule = %{permission, pattern, action}` with `action ∈ allow|ask|deny`) — per-session ruleset without touching global config.
3. **Reactive**: subscribe to `permission.asked` and call `permission_reply(id, %{reply: "always"})` — useful if we ever want a policy hook in Elixir instead of static rules.

The `--auto` flag documented on /docs/permissions ("automatically approve undenied requests") is a CLI run flag; whether `opencode serve` accepts it was not verified — use config rules for server mode.

## 4. Custom provider / local vLLM

Verified from /docs/providers: OpenAI-compatible endpoints use the `@ai-sdk/openai-compatible` loader via config — no code needed:

```json
{
  "provider": {
    "vllm": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Local vLLM",
      "options": { "baseURL": "http://127.0.0.1:8000/v1" },
      "models": { "qwen3-coder": { "name": "Qwen3 Coder", "limit": { "context": 131072, "output": 32768 } } }
    }
  },
  "model": "vllm/qwen3-coder"
}
```

- Pass exactly this map as `OpenCode.create(config: %{...})` (→ `OPENCODE_CONFIG_CONTENT`, highest-precedence config source per /docs/config).
- Per-session: `session_create` body `model: %{providerID: "vllm", id: "qwen3-coder"}`; per-prompt: prompt body `model: %{providerID: "vllm", modelID: "qwen3-coder"}` (note the two bodies use different key names — `id` vs `modelID` — per the spec).
- `apiKey` supports `{env:VAR}` interpolation; use `"@ai-sdk/openai"` instead if the endpoint speaks `/v1/responses` rather than `/v1/chat/completions`.

## 5. Maturity and pinning risk vs. raw Req

**Package facts** (hex.pm API): 89 releases from 2026-02-05 (v0.1.0) to 2026-08-11 (v0.1.88), near-daily during peak; ~5.6k all-time downloads (small user base). Unofficial ("Not affiliated with or built by the OpenCode team" — its own mix.exs description). Runtime deps: only `req ~> 0.5.0` and `jason ~> 1.2`. Regenerated by a bundled `mix opencode.gen.client` task from a checked-in spec snapshot; bundled spec corresponds to opencode server ~v1.1.53.

**Quality observations from source:**

- Responses are plain string-keyed maps. `OpenCode.Client.request/1` ignores the generated `response:` type info entirely — the 1,000+ generated structs and `@spec`s (e.g. `{:ok, OpenCode.Generated.Session.t()}`) are documentation only and never instantiated. Don't rely on the typespecs.
- SSE: workable but minimal — spawn_linked reader, manual buffer split on `"\n\n"`, no reconnect, no heartbeat handling, `{:error, e}` surfaced as a stream element.
- `OpenCode.Server` is a bare struct + raw `Port`, not a GenServer: no supervision, and `Port.close/1` closes stdio but does not guarantee the OS process dies — we'd want our own supervised wrapper (or `MuonTrap`-style management) regardless.
- Churn tracks the opencode server API (which is pre-1.0-style: `session.next.*` events, `experimental_*` and `worktree_*` routes are new-ish; the permission route moved from `/session/{id}/permissions/{pid}` to `/permission/{id}/reply` and the SDK carries both). Version drift is between the *server binary we run* and the *spec snapshot the SDK was generated from* — pinning the hex package only helps if we also pin the opencode binary version.

**What Req-direct would cost us:** the endpoints are trivial JSON-over-HTTP (the SDK's own client proves Req handles it, SSE included, in ~150 lines). We'd hand-write only the ~10 calls we use. What we'd lose: the generated endpoint catalog as discoverable docs, and free updates when the API moves (mitigated by reading `/doc` — the server serves its own OpenAPI 3.1 spec).

**Recommendation:** use `opencode_sdk` pinned exact (`{:opencode_sdk, "0.1.88"}`), pin the opencode binary version alongside it (health check `global_health/1` returns the server version — assert it at boot), and wrap the three touchpoints we own behind one small module (`Bench.Coder`?): server supervision, event-stream supervision/reconnect, and the reply/prompt calls. That keeps a Req-direct fallback a day's work, not a rewrite.

- Whether `opencode serve` honors `--auto`.

- Hexdocs (hexdocs.pm/opencode_sdk) was read via the repo's identical moduledocs rather than the rendered site.
